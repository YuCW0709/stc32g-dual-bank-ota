## 一、编译器与内存模型（C251 特有）

### P01 · `IAP_CMD` 写反，会静默抹掉 Bootloader

**现象**：程序跑飞、上电无法跳转，重新烧录才能恢复。没有任何报错。

**根因**：STC 的 IAP 寄存器组里 `IAP_CMD` 的含义是
`0`=空闲 `1`=读 `2`=写 `3`=扇区擦。写反一个数字，擦除就发生在你以为在写的地方。
更糟的是它在 BL 自己的地址空间上执行。

**判据**：任何写 Flash 的代码，注释里必须逐字标出 `0/1/2/3` 的语义；
改完先跑“读证”——读出目标扇区确认内容符合预期，再跑写测试。

**修法**：`flash_iap.c` 里把命令值定义成具名宏，禁止裸数字。

---

### P02 · L251 必须 `NOOVERLAY`，否则形参互相踩

**现象**：函数第一次调用正常、第二次返回垃圾；或者加一行无关的代码，别处的功能就坏了。

**根因**：L251 默认做 **overlay**（把不同函数的局部变量/参数块复用同一块内存）。
我们大量使用 `static xdata` + 手动状态机，编译器无法正确推断生命周期，
于是两个变量的地址被安排成同一个。

**判据**：看 `.m51` 里参数块地址是否重叠；`check_overlay.py` 会直接解析并报错。

**修法**：
- **两个工程都要在 Misc controls 里加 `NOOVERLAY`**（不是 C251 页！）
- 构建期用 `check_overlay.py` 守门（exit 7）

---

### P03 · 必须 LARGE 模型 + 函数指针要声明为 generic

**现象**：指针调用跳到错误地址，或者取到的函数地址只有低 16 位。

**根因**：SMALL/COMPACT 模型下函数指针是 2 字节，装不下 24 位 code 地址。
本项目 code 域基址是 `0xFE0000`（IAP）+ 偏移，必然超过 16 位。

**修法**：LARGE 模型 + `OTA_PTR_GENERIC=1`，函数指针一律 generic。

---

### P04 · APP 入口必须是 `?C_C51STARTUP` 落在 `0xFF4000`

**现象**：BL 跳过去直接跑飞，或者跳到一半的初始化代码。

**根因**：C251 的启动代码（`?C_C51STARTUP`）不在段首时，直接跳到段首会执行到
未初始化的数据段。APP 的第一条指令必须是编译器生成的启动代码。

**判据**：`check_layout.py` 校验符号 `?C_C51STARTUP` 的地址 == `0xFF4000`；
镜像首字节必须是 `0x75`（`MOV` 指令，C251 启动代码的固定开头）。

**修法**：`project` 里用 `CODE(0xFF4000)` 钉死起始段；`make_img.py` 打包前断言首字节。

---

### P05 · 缓冲一律 `static` 且**手动初始化**

**现象**：上电后缓冲里是 `0xFF` 而不是 0，解析出莫名其妙的字节。

**根因**：`static xdata` 的**初值不生效**，隐式零初始化也**不生效** —— 上电就是 `0xFF`
（Flash 擦除态）。C251 不会替你清零。

**判据**：在 `init` 里逐个字段赋 0，并在自检日志里打印几个关键变量。

**修法**：所有 `static xdata` 缓冲在使用前显式清零；不要依赖 `= {0}`。

---

### P06 · 栈只有 256 B，>32 B 的对象不许上栈

**现象**：函数返回地址被覆盖，跳到随机地址；局部数组稍大就崩。

**根因**：STC32G 的 C251 栈是固定 256 B，且**没有栈溢出检测**。

**判据**：`.map` 里看栈使用量；任何局部数组/结构体 > 32 B 就该怀疑。

**修法**：所有大对象改 `static xdata`；日志格式化也用全局缓冲。

---

### P07 · 不许给数据加 `code` 限定

**现象**：读常量读出半个字，或者 `memcpy` 搬一半就停。

**根因**：`code` 限定在 C251 上生成 16 位基址的取址指令，而我们的常量区基址超过 16 位，
取址只搬 `WORD0`，高字节丢失。

**修法**：APP 侧 const 一律不加 `code`；把这条例写进代码规范。

---

### P08 · 多字节 IAP 必须整段 `EA=0`，并且每 32 B 喂狗

**现象**：擦写过程中偶发复位（看门狗），或者写入数据错位。

**根因**：IAP 擦写期间 CPU 取指被挂起，如果中途有中断会读到不一致状态；
而一次擦除耗时远超看门狗周期。

**修法**：整段操作 `EA=0`；循环里每 32 B 调 `bsp_wdt_feed()`。

## 二、串口与 AT 引擎

### P09 · 两个不同含义的宏绝不能同名（C251 静默取第一个，0 warning）

**现象**：`+MSUB` 长行永远解析不出来，前缀永不匹配，但**没有任何编译告警**。

**根因**：`AT_URC_MAX` 同时被定义成“URC 注册表容量 8”和“行缓冲长度 88”。
C251 取第一个（8），于是行缓冲实际只有 8 B，62 字节的 `+MSUB` 被撕成 8 段，
前缀永远对不上，解析函数**从未被调用过**。

**判据**：症状是“完全没反应，且一行日志都没有” ⇒ 先怀疑**根本没进那个函数**，
（连 `ignored` 类分支都没打）而不是解析写错了。

**修法**：拆成 `AT_URC_SLOT_MAX=8` / `AT_URC_MAX=128`。
**给所有宏加含义后缀**，禁止一个名字两种用途。

---

### P10 · 接收热路径每字节超过 87 µs，就整字节丢

**现象**：模组侧发出 22 B 的应答，MCU 侧只收到 13 B；同一根线、相隔几百毫秒，结果不一致。

**根因**：**UART3 只有一个接收寄存器**。115200 下一字节 87 µs，
下一个字节到就把上一个覆盖 —— 不是“丢掉一部分”，是**整个字节消失**。
实测：只数不解的探针 6/6 次都是 22 B；带解析的旧热路径 13/22 B。
旧热路径每字节过 4 个函数调用 + 十几次 xdata 访问 ≈ **150 µs > 87 µs**。

**判据**：
- 写一个**只数不解**的探针（`at_rx_probe`），它和正式路径用同一根线、交替跑；
  两者长度不同 ⇒ 问题在固件，不在线上。
- 判据必须是**长度是否稳定**（N 次彼此相等），不许钉死某个具体字节数
  （那是模组专属值，换模组必然误报）。

**修法**：
- 热路径直接读 SFR，不进函数；
- 等待期间不碰环形缓冲；
- 映射（`\n` → 行）挪到收尾阶段。

### P11 · 主循环“抽稀”治不了丢字节，判据必须是**线路静默时间**

**现象**：`+MSUB` 行头还在、行内均匀丢 10 个字节（61 → 51），丢点间隔 4~10 字节。

**根因**：主循环一圈 = `data_poll + at_pump + mqtt_poll + 32 位比较` ≈ 50~90 µs，
刚好压在 87 µs 上；更早的版本是“每 8 圈做一次 `mqtt_poll`”，
于是**每 8 圈吃掉一个字节** —— 丢点看起来“随机”，其实是周期正好对上。

**为什么抽稀没用**：抽稀只保证“那一圈不慢”，不保证“别的圈不慢”。
只要还有**任何一个**周期性重活（MQTT 轮询 / 日志 / 以后新加的功能），
它就按自己的周期吃字节。

**判据**：**线路静默时间**（离上一个真实字节过了多久），不是“这一圈干了什么”。

**修法**：

```c
/* at_pump() 返回“这一次真从 SFR 取到字节”，主循环据此判线路是否还在动 */
t0 = at_ms();
for (;;) {
    if (at_pump() != 0U) t0 = at_ms();              /* 还在动，不许走 */
    else {
        data_poll();                                 /* 填在 AT 的空档里跑 */
        if ((u32)(at_ms() - t0) >= APP_AT_QUIET_MS) break;
    }
}
```

`APP_AT_QUIET_MS = 1` ⇒ 一字节 87 µs，**11 倍余量**。
判据用**毫秒**不用“圈数”：圈数等于把指令周期当常量，改一行代码就变。

**效果**：`urc [… ] n=51` → `n=61`，连续 6 次一个不丢。

### P12 · AT 命令窗口会吃掉 URC

**现象**：服务器连发 6 条 retained 消息，MCU 一条都没响应。

**根因**：订阅成功的那一毫秒里立刻发 `MPUB`，retained 消息在 `AT+MSUB` 的
命令窗口内到达，被应答扫描器当成“命令的响应”吃掉了。

**修法**：订阅成功后**静默 1.5 s** 再上报（`MQTT_SUB_QUIET_MS`）。

---

### P13 · `+MSUB` 的载荷带双引号，且 `N byte` 的 N **含引号**

**现象**：解析器把每条版本消息都判成“不是版本”，全部丢弃。

**根因**：手册示例不带引号，实际报文是

```
+MSUB: "fw/0001/ver",32 byte,"0.7.3|https://…"      裸串 30 B，报 32
```

照手册写解析器 ⇒ 首字符是 `"` ⇒ 判成非版本。
`N == 最后一个逗号之后到行尾的字符数`（含引号）—— 这一条**正好可以当长度校验**。

**修法**：跳过前导引号、URL 遇 `"` 截止；用 `N` 校验整行长度。
现场丢 1 字节就把 `0.7.1` 读成 `0.71`、`xoxgMU` 读成 `xogMU`，导致版本号错位 + 404。

---

### P14 · `AT+HTTPTERMATAT` 这种命令叠加，是漏了 `at_tx_reset()`

**现象**：模组回 100+ 行 `+CME ERROR: 58`。

**根因**：`at_tx_mac` 发完**不清**发送缓冲，下一条命令拼在残留内容后面，
变成 `AT+HTTPTERMAT`、`AT+HTTPTERMATAT`…（手写替代 `at_ping()` 时最容易漏）。

**修法**：任何手写发送路径都必须补 `at_tx_reset()`。

---

### P15 · 判据里不许出现某个模组的字节数/应答长度

**现象**：换模组后，一个健康链路被判成“丢字节 0/6”。

**根因**：旧判据钉死 `AT+IPR?` 应答 = 22 B（SIMCom 专属）。
换成 Air724 后应答长度不同，健康链路必然“不合格”。

**修法**：判据换成**通用性质**：“N 次读取的长度彼此相等（min == max）”。
**任何和具体型号绑定的常量都不能进判据。**

## 三、HTTP 下载与镜像

### P16 · `+HTTPACTION: 602` = 内存不足，必须用 `BREAK/BREAKEND` 分片

**现象**：整包 GET 一个 23 KB 的固件，`+HTTPACTION: 0,602,0`，永远拿不到数据。

**根因**：模组 HTTP 响应缓冲只有 3356 B（`HTTPREAD` 上限），整包必爆。

**修法**：

```
AT+HTTPPARA="BREAK",1024
AT+HTTPPARA="BREAKEND",1024
AT+HTTPACTION=0
```

服务器**必须支持 Range**（返回 `206` + `Content-Range`），否则无解。
`check_fw_url.py` 的第 7 项就是在守这一条。

> 601 = 网络错误（没卡/没注网/PDP 没起），**与 TLS 和 URL 无关**；602 = 内存不足。

---

### P17 · HTTPS 在 8910 平台上，SSL 配置要在 `HTTPINIT` **之前**

**现象**：`HTTPACTION` 一直超时，看不出任何 SSL 错误。

**根因**：Air724（8910 平台）的顺序是
`HTTPSSL=1` → `SSLCFG="seclevel",153,0` → `HTTPINIT` → `HTTPPARA="CID",1` → URL → `HTTPACTION=0`。
和 SIMCom 的顺序**相反**。

另外 **HTTPS 的第三个前提是系统时间**（`AT+CCLK?`）。时间没同步时 TLS 失败
只表现为 `HTTPACTION` 超时，没有任何提示。

---

### P18 · 镜像超长会被 512 对齐裁掉，打包必须 `--full`

**现象**：OTA 装完 CRC 对不上，或者镜像比预期短。

**根因**：APP 内容超过 ~48640 B 时，`make_img.py` 的自动裁剪会算出
`49152 > 49088`，装不下 64 B 头。默认逻辑会裁到 512 对齐的较小值。

**修法**：出包一律加 `--full`，并核对 `total = 64 + img_len`。
本项目镜像固定 `49152 = 64 头 + 49088 正文`。

---

### P19 · 落地必须自检，坏镜像要在**下完那一刻**就报

**现象**：下载“成功”、重启后 BL 报 `STAGING fail rc=12`，用户白等一轮。

**根因**：只信 HTTP 层的 `Content-Length`，不校验 Flash 里真实落下的内容。

**修法**：`HOTA_DONE` 时立刻回读 STAGING，校验 `magic / hdr_len / hdr_ver / img_len / 正文 CRC32`，
不通过就打 `stg crc now=… want=…` 并转 IDLE。
**两个 CRC 分开打**，才能区分“头没写进去”和“正文被改写”。

## 四、Bootloader 与分区

### P20 · 烧录器不擦 STAGING 与 PARAM

**现象**：以为“重新烧录 = 全新状态”，实际上一堆旧状态在起作用。

**根因**：合并 hex 只覆盖 IAP `0x10000` 以上。
实测 `merge_hex --info`：

```
0xFF0000-0xFF3F96   BOOTLOADER
0xFF4000-0xFFFB32   APP
```

**STAGING（`0x0000` 起）和 PARAM（`0xC000` 起）完全不在烧录范围内** ——
上一次 OTA 的镜像和参数会一直活着。要彻底干净必须勾“整片擦除”。

---

### P21 · BL 里任何“无条件动作”都会掩盖 APP 侧的修复

**现象**：重新烧了 `APP v0.8.2`，上电**直接开始搬运**，APP 一次都没跑起来，
连 MQTT 都没进。看起来像“烧录没生效”。

**根因**：BL 里有个诊断开关

```c
#define BL_OTA_A1_FORCE 1    /* 临时打开做 CRC 取样，注释写着"定位完立刻改回 0" */
if (p->ota_state == PENDING_REBOOT || (BL_OTA_A1_FORCE != 0)) { /* 校验 + 搬运 */ }
```

配合 P20（STAGING 里那份旧镜像一直活着且完好），
⇒ **每次上电都把 APP 覆盖成 STAGING 里那份旧版本**。

它上一次没暴露，只因为当时搬进去的**恰好还是同一份镜像** —— 换镜像立刻现形。

**判据**：给 BL 一个能自证的版本串，把开关值写进去：

```
==== BL v0.2 (A1FORCE=0) ====
（并且不应出现 "pending install -> verify staging"）
```

> 教训：**BL 之前一直是 `BL v0.1 (P0)` 永不变化**，导致无法从日志上区分
> “烧进去的是新 BL”还是“跑到旧 BL”，只能靠“有没有 pending install 那行”反推 ——
> 而那正是出问题的东西本身。**用症状证明症状，是排查里最危险的一步。**

**纪律**：
1. 临时开关必须带**到期条件**，定位完**当轮**改回，不许跨天。
2. 任何“无条件执行”的路径都要能一键关掉，并且关掉的状态要在启动日志里可见。

---

### P22 · payload 里的版本号只是字符串标签，装的是 URL 指向的字节

**现象**：发 `0.8.3|https://…/Ri6kyo`，设备安静地变成了 `v0.7.4`。

**根因**：`Ri6kyo` 是 0.7.4 的直链。版本号只用来做“要不要升”的比较，
**真正装进去的是 URL 指向的那份字节**。

**判据**：比对日志里的 `crc` 和本地镜像头的 `body_crc`：

```
日志   [VER] STAGING ok len=49088 crc=10538532
本地   build/fw_v0_7_4_ota.bin → body_crc = 0x10538532   ← 十进制 10538532，完全一致
```

**修法（工程侧）**：CI 里把“版本号 ↔ 镜像头 ver ↔ md5”三者绑成一条断言；
发布脚本只允许从“刚打完的镜像”推导出 payload 字符串，不许手写。

**修法（固件侧，进阶）**：落地自检时比对
**镜像头 `ver`（偏移 8..11）与订阅消息声明的版本**，不一致就拒绝安装。
注意只做“标签必须与内容一致”，**不做“只许升”** —— 回滚是合法需求。

## 五、工程纪律

### P23 · 日志系统的参数个数必须与实际一致

**现象**：日志打出 `!!ARGN!!`，或者打印出垃圾值。

**根因**：本项目日志是“先填一个数组，再按格式串消费”，`LOG_I2` 的 `2` 必须**精确等于**
后面可变参数的个数；一行里也不许超过 2 个值。
`%u` 与 `%lu` 在本实现里等价，但**格式符和值的类型要匹配**。

**判据**：行尾的 `*HH` 是行校验和，只能证明“线路没坏”，**不能证明内容对**。
和值错 = 抄写/桥接错误；和值对但内容怪 = 才去怀疑固件。

---

### P24 · 构建必须跑两次比 md5，且不许把改版本/编译/打包塞进一条 `&&`

**现象**：产物里混着上一个版本号；或者同一份代码两次构建大小不同。

**根因**：
- C251 的布局对“加一行注释”级别改动都可能敏感 ⇒ **两次 md5 不一致 = 有未定义行为**。
- `sed` 改版本 + build + 打包写在一条 `&&` 里时，中途失败会留下“旧代码配新版本号”的产物。

**修法**：
1. 改版本 → 编译 → 打包 **三步分开**，每步都验证；
2. 每次交付前 `md5sum` 跑两遍；
3. 用 `hex` 解包复查版本串是否真的在镜像里（`APP v0.8.2` @ 某个地址）。

## 附：一次“什么都没反应”的排查顺序

按这个顺序走，能省掉大部分弯路：

1. **连 `ignored` 类分支都没打？** → 根本没进那个函数（P09）。
2. **进了函数但一行日志都没有？** → 看日志系统本身（P23）。
3. **行拼出来了但前缀不匹配？** → 打印**原始行 + 长度**（`urc [%s] n=%u`）。
4. **长度不足？** → 是“线路丢”还是“读得太慢”？（P10 / P11：只数不解的探针）
5. **长度够但内容坏？** → 逐字节比对，看丢点是否均匀（均匀 = 周期性重活）。
6. **内容对但行为不对？** → 才去看业务逻辑。

> 这套顺序的价值在于：**每一步都在缩小“问题在哪一层”，而不是猜。**
